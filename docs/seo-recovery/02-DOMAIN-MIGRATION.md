Raw property sums are 33 clicks / 6,154 impressions over the matched 28 days, and 64 clicks / 13,360 impressions over the matched 51 days. These are **not deduplicated site totals**: query/page overlap can cause the same search activity to appear under both properties. No combined average position is reported because averaging property positions would be misleading and the exports do not allow reliable deduplication.

The old-domain 28-day history fell from 26 clicks / 6,336 impressions (25 Aug–21 Sep) to 10 / 1,802 (22 Sep–19 Oct), while its reported average position improved from 21.79 to 13.48. The new-domain export has 23 clicks / 4,352 impressions for the latest 28 days. This establishes continuing visibility on the new property; it does not by itself establish how much traffic transferred, because the first new-domain daily row is 30 August and the properties overlap.

One brand-query comparison in the matched 51-day export supports transfer: `zq removals` had 2 clicks / 95 impressions on the old property and 13 / 90 on the new property. Query-level rows are privacy-filtered and do not sum to property totals. These observations are not causal proof of the migration's effect.

### Repeatable post-deployment verification

Added `scripts/verify-migrated-guides.mjs` and `npm run seo:verify-migrated-guides`. It checks the three aliases return one permanent response directly to the canonical destination, each deployed destination returns 200 with one indexable canonical, and every destination appears in the guide sitemap. Run first against the authorized Preview deployment:

```powershell
npm run seo:verify-migrated-guides -- --origin https://<ready-preview-deployment-host>
```

After an authorized Production deployment, additionally test the historical host:

```powershell
npm run seo:verify-migrated-guides -- --origin https://zqremovalsadelaide.com.au --legacy-origin https://zqremovals.au
```

The legacy-origin option requires one permanent hop directly to each intended canonical URL. The current Production's known 308 same-path host redirect would fail this check until the legacy-host/domain redirect behavior is corrected. The current Production deployment and this branch have not been conflated; no live fix is claimed.

## Redirect order and platform metadata follow-up — 23 October 2026

Read-only Vercel inspection found **zero project-level route rules** and the old and new project domains have no configured domain redirect target. The source-level Production deployment configuration therefore explains the observed 308→404 chain: the deployed historical `vercel.json` has host-conditioned catch-all rules for `zqremovals.au` and `www.zqremovals.au` that preserve `:path`, while that deployment does not include the three exact migrated-guide redirects. The redirect sends each old URL to the same new-domain path, where it is a 404.

The reviewed branch already has three exact permanent mappings to the corresponding canonical guide routes before those host catch-alls. The regression test now asserts every exact guide mapping precedes the catch-all rule, and asserts the destination exists in the sitemap and is not itself indexed as an alias. This is the safest correction available in repository code; no Vercel domain settings were changed. It remains **PREPARED / NOT DEPLOYED** until an authorized Preview deployment proves one direct 308→200 hop and the verifier passes. If the deployed branch still reaches a same-path 404, inspect Vercel project routes and domain forwarding again before adding another rule.
