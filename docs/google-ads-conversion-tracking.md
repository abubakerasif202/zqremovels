# Google Ads conversion tracking implementation

Status: website changes implemented; account configuration and production verification PENDING. No push, deployment, GTM publication or Google Ads account mutation is authorized by this change.

## Architecture and audit findings

The production build is `npm run build` → `scripts/build-site.mjs` → Astro static build → generator post-processing → `site-dist`. Routing is generated by `src/pages/[...slug].astro` from `site-src/pages.json` plus generated route registries. `src/layouts/Layout.astro` owns live tracking installation. This is not Next.js or React and has no client router/component hydration. Vercel serves the generated static files, permanent redirects and CSP from `vercel.json`, plus the separate `api/quote.js` function.

The layout contains the fixed container `GTM-WJGKPXFL`. Optional environment configuration can load standalone GA4 (`VITE_GA_MEASUREMENT_ID` or `GA_MEASUREMENT_ID`) and Meta Pixel; neither an environment ID nor a source-code reference proves a working live destination. Legacy tracking renderer functions in `scripts/build-site.mjs` are unused by the Astro render path. No new standalone Ads library or invented label is installed. Confirmed target supplied by the owner: `AW-18413688842`.

All generated quote forms use `data-quote-form="quote"` and the common `site.js` handler. Source inspection found homepage hero and short forms, contact form, Ads landing forms, reusable Astro QuoteForm, and legacy suburb form markup. Output inspection identified a Southern Adelaide form still posting to a static thank-you URL with obsolete Netlify attributes; it is now wired to the same provider acceptance handler, with its existing fields mapped to the submission payload and a status message. Other historical suburb markup is replaced or consolidated by the generator. The historical Google Ads quote landing route is consolidated, so browser coverage uses its real surviving forms. The active browser flow posts directly to Web3Forms, NOT `/api/quote`. Native submissions without JavaScript post to the provider and are intentionally not measured by a thank-you page view. The API route is retained and now also requires explicit upstream acceptance. Design kit forms are not customer enquiry endpoints.

Original problems:

- Empty, malformed or non-JSON HTTP 200 responses were treated as successful enquiries.
- Loading the public thank-you page fired success tracking, including optional direct Ads conversion and Meta Lead events.
- `generate_lead` lived in the submit utility rather than the confirmed success utility; the caller happened to invoke it after the request but lacked reliable confirmation and deduplication.
- Events were dispatched through both gtag and dataLayer; optional Ads configuration supplied another conversion path.
- Quote clicks and form starts sent Meta Lead events despite no accepted enquiry.
- Attribution query values were spread into event parameters, potentially carrying personal details; query strings were included in custom page views.
- No repository CMP, consent preference UI, consent mode commands or enhanced-conversion user-data implementation was found. A CMP injected in the remote GTM container cannot be ruled out without access.
- Telephone handling emitted both `phone_click` and `call_click`. No genuine WhatsApp CTA was found in production source.

## Website event contract

| Action | Event | Fields | Ads role |
| --- | --- | --- | --- |
| Provider accepts quote | `generate_lead` | `lead_type=removal_quote`, `form_name`, `lead_id` | Primary |
| Verified connected/qualified call | `qualified_phone_lead` | Supplied only by a verified call system | Primary only when verified |
| Business telephone click | `phone_click` | `contact_method=phone`, `link_location`, `page_path` | Secondary |
| WhatsApp contact click | `whatsapp_click` | `contact_method=whatsapp`, `link_location`, `page_path` | Secondary |
| Contact or other page view | `page_view` | `page_path` | Analytics only |

`generate_lead` is pushed only for HTTP success AND JSON `success === true`. Invalid, rejected, failed, empty and malformed replies never qualify. A form is locked while submitting and after acceptance, including restoration of the same document from browser history. Explicit `data-form-name` is preserved; fallback names include route and form index, distinguishing multiple homepage forms.

When available a validated opaque `lead_id` from the accepted response is used. Otherwise a random UUID is created **after acceptance** solely as an event deduplication token; it is not a CRM receipt or proof of email delivery. The data layer push occurs before navigation, with GTM `eventCallback`/`eventTimeout` and a bounded browser timeout. Memory and session storage suppress a repeat token. Blocked storage does not prevent enquiry completion. GTM/Ads failure never changes provider acceptance into a failed enquiry. No phone, email, customer name, address, form values or raw attribution fields enter these conversion events. URL attribution remains available to the existing enquiry submission flow.

Deduplication does not make the remote Web3Forms endpoint idempotent across new documents, separate devices, or ambiguous network timeouts. There is no durable lead database in this repository. A future durable backend receipt and provider idempotency support would be needed for that guarantee. Do not retry a genuinely accepted enquiry solely because a tracking hit was blocked.

Telephone tracking matches only the supplied business number (local/international formatting), preserves link behaviour, and uses one guarded delegated listener. WhatsApp matching accepts HTTPS `wa.me`, `api.whatsapp.com/send` and `web.whatsapp.com/send` endpoints; no new contact link or business channel has been invented. Tests use a synthetic link because the site has no real WhatsApp CTA.

### Consent Mode V2 and enhanced conversions

The layout queues denied defaults for `ad_storage`, `analytics_storage`, `ad_user_data`, `ad_personalization` before GTM, unless an existing consent command was already queued. Existing queued decisions retain ownership and are never silently granted or overwritten. This is advanced-mode default denial, not a CMP or consent collection UI. Google tags may send consent-aware cookieless signals. No banner was added because remote CMP configuration cannot be inspected safely from the repository.

Inspect the GTM **Consent Initialization** CMP tag and its persisted preference restoration first. Configure all four types through its supported consent APIs, restore saved choices before other tags, and emit updates only after a real user choice. Test accept, reject, partial consent and return visits in Preview. Without an existing CMP/approved preference interface, defaults remain denied; obtaining consent and enabling storage remains an account/integration prerequisite. This can reduce measurement and must be resolved before calling the system production verified. Do not add an unconditional grant to recover reporting.

Use built-in consent checks for Google tags and inspect effective consent in Preview; use additional requirements where needed to block user-data processing. Do not bypass consent for conversions. Optional Meta and other non-Google tags require their own CMP blocking rules; Google consent mode alone does not control them.

Enhanced conversions are **not enabled by this implementation**. In Ads inspect the quote action's enhanced-conversion setting and account customer-data terms. If approved, configure supported Google Ads/GTM user-provided-data mechanisms with consent-gated `ad_user_data=granted`, correct normalization/hashing and restricted variable access. Disable automatic form/DOM user-data collection until this is approved. Never place customer details in standard dataLayer events, logs or URL parameters. No inferred consent from submitting a quote.
